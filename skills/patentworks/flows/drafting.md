# Flow: Drafting(起草專利說明書)

從技術揭露,起草符合目標法域的**請求項 + 說明書 + 摘要**。撰寫知識條列在 `../reference/drafting/`。

## 0. 定法域,載入知識
- 先確認**目標法域**:必載 `reference/drafting/common.md`(跨法域共通)+ 以下其一/多個:
  `tw.md` / `cn.md` / `us.md` / `ep.md`。
- 起草全程**對著載入的條列規則寫與自檢**。法遵是 skill 知識,**不呼叫工具**。

## 1. 揭露與分析擷取 (Disclosure & Analysis)
- **優先讀取 `AnalysisOutput`**：如果已執行分析流程，優先從其結構化欄位（如 `draftingBasis`、`technicalFeatures` 與 `elementMap`）直接載入技術問題、手段、效果與必要/非必要特徵。
- 若無分析產物，則從原始技術交底書（Disclosure）中擷取：技術問題、技術方案、有益效果、必要技術特徵、實施例、附圖構想。
- 列出「擬保護的創新點」清單（或從 `claimSeeds` 開始），確保保護範圍全面。

## 2. (選)前案定位與差異劃界
- 若尚未進行分析，且需要確認最接近前案以定出**差異點/區別技術特徵**，應優先呼叫 `analysis.md` 對前案與本案特徵進行對照。
- 根據 `AnalysisOutput` 的 `closestPriorArt` 與 `differences` 進行獨立請求項的劃界與進步性論述。

## 3. 請求項先行(claims-first)
- 先寫權利要求(它主導保護範圍),說明書再來支持。
- 獨立權利要求:**兩段式**(前序=主題+共有必要特徵;特徵部分=區別於最接近前案的特徵)。不缺必要特徵、不堆非必要特徵。
- 從屬權利要求:逐層遞進限定,範圍落在被引用項內;擇一引用避免邏輯斷裂。
- **多面向保護**(視法域):方法 / 裝置·系統 / 電子設備 / 電腦可讀介質。
- 句式、劃界、回引規範依**法域檔**(CN 見 cn.md;US 見 us.md;…)。

## 4. 說明書支持請求項(spec supports claims)
- 章節順序:技術領域 → 背景技術(公知基礎+最接近現有技術+技術性缺點)→ 發明內容(**目的→方案→效果** 邏輯鏈,用語對應獨權)→ 附圖說明 → 具體實施方式。
- **具體實施方式**須使每個請求項特徵具體化、本領域技術人員可重現;概括性/功能性特徵須給數個實施方式支持。
- **術語一致**:全文同一事物同一名稱;按步驟/層次寫,不按功能寫。

## 5. 摘要
- 名稱+領域+技術問題+方案要點+主要用途;附圖標記加括號;指定一幅摘要附圖。字數依法域(CN ≤300 字)。

## 6. 圖式
- 流程圖/結構圖/時序圖。專利風格(黑白線稿 + 參考編號疊加)由 **drawmiat 第三模式**(待建)產出;暫時可先出 drawing brief。

## 7. 法遵自檢(skill 知識,逐條對照)
- 對照 `common.md` + 法域檔逐條檢查:充分公開/可據以實施、請求項清楚簡明、獨權必要特徵齊備、前置基礎(antecedent basis)、新穎/進步性以請求項為準、字數與格式、不授權客體規避等。
- 標出疑點交人類複核;**AI 不做最終裁決**。

## 8. 交付
- 說明書以 markdown 起草 → docxmcp 組裝成 docx(或 stage_file 落地)→ 回 token+download_url handle。人類可讀文件是交付契約。
