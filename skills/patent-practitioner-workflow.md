# 專利從業者檢索實務 Workflow（領域參考）

> 本文記錄專利從業人員（專利工程師／檢索分析師／專利師）進行專利檢索與判讀的**實際人類流程**，作為本 repo 各 AI skill 的設計依據。先忠實描述人類怎麼做，最後一節說明 AI 該怎麼「對應而非照抄」。

> **⚠️ 輸出不變式（硬性契約，無例外）**：不論 AI 內部如何處理（fan-out、可拋棄 worker、handle 化…），**任何 patent search 的最終交付物一律是「人類看得懂的表格（spreadsheet）」**——這是所有檢索類型共通的產業慣例。AI 的內部方法自由，**輸出契約固定**。表須保留可稽核的原始欄位（PN/TI/AB/相關 CL/申請人/日期/CPC）並排 AI 加值欄（相關性判定＋理由＋命中要件），以 xlsx 經 blob handle 交付。

---

## 一、先分清楚:檢索的「目的」決定整個流程

業內不存在單一「專利檢索」。目的不同，策略、資料庫、判讀標準、產出全都不同:

| 檢索類型 | 問題 | 重點 |
|---|---|---|
| **可專利性 / 前案檢索**（Patentability / Prior Art） | 我的發明是否新穎、有進步性? | 找**最接近的前案**;看是否單篇揭露全部特徵(新穎性)、或數篇組合可顯而易見(進步性) |
| **技術現況 / 地圖**（State-of-the-art / Landscape） | 這個領域有人做過什麼? | 廣度優先,看趨勢、主要申請人、技術分支 |
| **侵權迴避 / FTO**（Freedom-to-Operate） | 我能不能做/賣而不侵權? | 只看**有效專利的請求項**,且限**目標市場國別**;讀獨立項是否 read on 我的產品 |
| **有效性 / 無效檢索**（Validity / Invalidity） | 能不能打掉某件專利? | 針對**特定一件專利的請求項**,找它申請日前的前案 |

> 使用者範例「居家異常聲音偵測有沒有人做過」= **技術現況 + 可專利性**(廣度掃描 + 找最接近前案)。

## 二、端到端流程(以前案/現況檢索為主軸)

### 1. 釐清標的（Define）
- 拆解發明的**技術問題 — 技術手段 — 技術效果**。
- 抽出**核心技術特徵**(要件),這些才是後面比對的基準。
- 界定範圍:國別、年代、案件類型(發明/新型/設計)。

### 2. 擬定檢索策略（Strategy）—— 概念區塊法
把問題拆成幾個**概念區塊(concept blocks)**,每塊各自展開同義詞/分類,再用布林組合:

- **分類號**(最穩的召回骨幹):CPC / IPC。分類是審查員標的、**語言中性**,跨國檢索靠它。
- **關鍵詞**:每個概念的同義詞、上下位詞、**中英(跨國要多語)**。例:異常聲音 = abnormal/anomalous sound、acoustic anomaly、異音、異常音。
- **申請人 / 發明人**:鎖定領域主要玩家。
- **日期 / 優先權**:可專利性看申請日前;有效性看標的專利申請日前。

> 鐵則:**檢索一律以分類號(CPC/IPC)做領域限縮**,關鍵詞在域內補刀。純關鍵詞召回不穩、跨語言失準。

### 3. 執行與迭代（Execute & Refine）
- 概念區塊以 AND 串、同義詞以 OR 並、雜訊以 NOT 排。
- 看命中總數:太多→加條件收斂;太少→放寬同義詞/分類。
- **反覆迭代**到「可人工逐筆判讀的量」(通常數十到一兩百筆)。

### 4. 篩選判讀（Screen）—— 這是最耗工、最核心的一步
- 把命中匯出成 **spreadsheet**(業界慣例的工作面)。
- 逐列讀 **title → abstract → (claims / 代表圖)**,**逐筆解讀語意**,標記 相關 / 可能 / 不相關。
- 判讀的問句:
  - 是否處理**同一技術問題**?
  - 是否用**相同/近似的技術手段**(核心要件)?
  - (新穎性)單篇是否揭露**全部要件**?
  - (進步性)數篇組合是否使本案**顯而易見**?
  - (FTO)**獨立項**是否涵蓋我的產品?

### 5. 深讀與比對（Analyze）
- 對「相關」的少數,深讀**請求項**(尤其獨立項)。
- 做**要件對照表(claim chart / feature matrix)**:本案要件 × 前案揭露,逐格標 揭露/未揭露/部分。
- 評估「最接近前案」與本案的差異點(可作為新穎/進步性論述或迴避設計依據)。

### 6. 雪球擴張（Snowball）
從一件關鍵相關前案,沿以下邊界擴張,常能撈到關鍵詞漏掉的:
- **後向引用**(它引用了誰)、**前向引用**(誰引用它)
- **專利家族**(同一發明的他國對應案)
- **同申請人 / 同發明人**的相鄰案

### 7. 出報告（Report）
檢索報告通常含:檢索目的與範圍、策略與檢索式、資料庫與日期、**關鍵前案清單(附相關性理由)**、要件對照表、結論(可專利性/FTO 風險評估)。

## 三、判讀 spreadsheet 的典型欄位

| 欄位 | 說明 |
|---|---|
| 公開/公告號 PN | 識別 |
| 專利名稱 TI | 第一眼篩 |
| 摘要 AB | 主要語意判讀依據 |
| (相關)請求項 CL | 深讀、要件比對 |
| 申請人 / 發明人 | 玩家、雪球線索 |
| 公開/申請/優先權日 | 前案資格判定 |
| CPC/IPC | 領域、再擴張線索 |
| **相關性 判定** | 相關/可能/不相關 |
| **理由 / 命中要件** | 為何相關、命中哪個特徵 |

## 四、AI 該如何「對應」而非「照抄」這個流程

人類逐列讀整張表,是因為一次只能讀一行。AI 的調整有兩個原則。

### 原則 1:判讀靠「摘要」,規模其實很小,單 agent 即可
- 相關性判讀讀的是**摘要**(~300 token/篇),不是完整 claims/說明書。
- 幾十筆候選的摘要 ≈ 1 萬 token,**單一 agent 分批讀完即可,不需要開 subagent**。
- 只對「通過摘要篩」的少數,才深讀完整 claims 做要件比對(那才是 2k–20k token/篇的重內容)。
- (平行 fan-out judge 是真實但**有上限(約同時 10–16 個)、耗 token** 的能力,僅在候選上百筆、或需對多篇讀完整 claims 時才動用——**非預設**。)

### 原則 2:每讀一篇,就在表上「存下蒸餾」——別讓花掉的 token 蒸發
讀一篇是有成本的;若只輸出「相關 Y/N」就丟掉,等於白讀。每讀一篇,寫回一格**壓縮過的判讀產物**(是壓縮,不是回貼原文):

| 寫回該列 | 內容 |
|---|---|
| 相關性 + 分數 | 相關/可能/否 + H/M/L |
| **技術要點(1–2 句蒸餾)** | 這篇實際在做什麼,**用本案的語彙**講 |
| **命中/落差要件** | 揭露了本案哪些要件、缺哪些 |
| 一句理由 | 為何這樣判 |

讀 ~300 token → 寫 ~50 token:輸出不臃腫,但**理解被存進表裡**。這一格**三合一**:人類交付物 + 稽核依據 + 可重用的 **RAG 蒸餾**(下次再碰這篇不必重讀)。

### 串起來
1. **召回**:CPC + 關鍵詞 → 候選列(只 pn/title/節選,極小)。
2. **判讀**:單 agent 分批讀摘要,**每篇寫回壓縮蒸餾 + 判定**到表。
3. **深讀**:僅 shortlist 讀完整 claims,補要件對照。
4. **雪球**:沿 family/citations 擴張,再餵回判讀。
5. **複核**:AI 預篩+評分+解釋,人複核 borderline(前案有法律份量)。

> 一句話:**表是 AI 篩選的「結果」,不是 AI 思考的「現場」;而 AI 每一次閱讀都該在表上沉澱成可重用的蒸餾,不讓 token 白花。**

## 四之二、Screening 作業參數(硬規格)

| 參數 | 值 |
|---|---|
| **單次分析上限** | **300 件**;每件帶 **PatNo / Title / Abstract / Claim1**(只取獨立項，足以判相關性) |
| **命中 >300 件** | **不分析，先「再篩選」收斂**(加嚴 CPC/關鍵詞/日期)，不讓結果發散 |
| **工作介質** | agent **爬這個 excel、逐格消化**，每格寫回壓縮蒸餾(見 §四原則 2) |
| **降成本前處理** | **家族去重 + 保留家族關聯欄**:同一 INPADOC 家族的 US/CN/EP 成員是同一發明，收斂成一個代表列 + 列出成員，**只消化代表一次**(其餘標「同家族，見代表」)。300 命中常收斂成 ~180 家族 → 消化量少約四成 |

**裝配流程**:
```
search(優先 GPSS, CPC+關鍵詞) → 命中數
  ├─ >300 → 回「太發散 + 建議收斂方式」,不繼續分析
  └─ ≤300 → 組去重 excel(PatNo/Title/Abstract/Claim1/family_id/members) → blob
            → agent 爬 excel 逐格消化,寫回 蒸餾 + 判定 + 命中要件
            → 交付同一張 enriched excel
```

> 來源注記:GPSS 的 search 一次呼叫即回 PatNo/Title/Abstract/Claims(`expFld`),最適合裝配此表;Claim1 由 CL 切首項。家族 family_id 是否由 GPSS 直接提供待核准後實測;若無,以 EPO INPADOC / Google family 補。

## 五、本生產線的分工對應

- **MCP tool**:`search`(候選列)、`get`(完整摘要+claims)、`stage_*`(PDF/代表圖/全文 → blob handle)。
- **skill**(待建,如 `patent-screening`):編排「search → fan-out judge → 評分 xlsx」。
- **xlsx skill / docxmcp**:把結果列落地成 spreadsheet/報告,經 token+blob handle 交付。
- 資料來源優先序:GPSS(首選)> Google Patents(語義排序+代表圖)> EPO(家族/引用)。
